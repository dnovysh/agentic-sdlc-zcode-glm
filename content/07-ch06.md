# Глава 6. Агент должен видеть результат своей работы

Единственный способ для агента убедиться, что он всё сделал правильно, — собрать проект и проверить результат так же, как проверил бы человек. Без такой возможности он считает работу законченной, как только она выглядит готовой. Эта глава показывает, как дать агенту эту возможность: сначала локально, потом на превью-стенде и в браузере.

## Скрипт, который поднимает проект с нуля

Чтобы проверять работу как человек, агенту нужно полноценное окружение. Проще всего собрать проект целиком у себя: и фронтенд, и бэкенд, и базу.

Лучше всего, когда весь подъём выполняется одной командой. Если такой команды нет и сборка — это цепочка шагов после каждого из которых нужно смотреть на результат, тоже не беда. Важно, чтобы цепочка была понятной и одинаковой: каждый раз она должна давать один и тот же результат.

Цепочку можно описать текстом в `AGENTS.md`, но надёжнее записать её в скрипт. Текст агент читает заново каждый раз и может понять по-своему, а скрипт выполняется одинаково.

Для команды, где есть и Linux, и Windows, удобнее всего один скрипт на Node.js или Python: он одинаково работает на всех системах, и агенту не нужно выбирать. Ниже каркас такого скрипта. Он печатает только ошибки и в конце адрес приложения.

```javascript
// scripts/up.mjs — поднимает проект с нуля на Linux, macOS и Windows.
import { spawnSync } from "node:child_process";

function run(label, cmd, args) {
  // На Windows npm — это npm.cmd, такие файлы запускают через shell.
  const shell = process.platform === "win32";
  const r = spawnSync(cmd, args, { stdio: ["ignore", "pipe", "pipe"], shell });
  if (r.status !== 0) {
    console.error(`Шаг «${label}» не выполнен: ${cmd} ${args.join(" ")}`);
    console.error(String(r.stderr || r.stdout).split("\n").slice(-15).join("\n"));
    process.exit(1);
  }
}

run("установка зависимостей", "npm", ["ci"]);
run("миграции", "npm", ["run", "db:migrate"]);
run("тестовые данные", "npm", ["run", "db:seed"]);
console.log("Готово. Приложение: http://localhost:3000");
```

Если в команде приняты классические скрипты, держите их парой: `scripts/up.sh` и `scripts/up.ps1`. К скриптам предъявляются четыре требования.

- **Повторный запуск ничего не ломает.** Запустили второй раз — получили тот же результат.
- **Чего-то не хватает — скрипт говорит, чего именно и как это поставить, и останавливается.**
- **Успешные шаги не печатаются.** Тысяча строк успешной сборки занимает контекст, который лучше потратить на задачу.
- **Скрипт проверен с нуля несколько раз.** Агент может взять не ту команду или пропустить шаг, который все делают по памяти, поэтому пусть он прогонит скрипт, удалив всё установленное.

Запускаются такие скрипты по-разному в зависимости от системы.

```bash
bash scripts/up.sh && bash scripts/check.sh
```

```powershell
pwsh -NoProfile -File scripts/up.ps1
pwsh -NoProfile -File scripts/check.ps1
```

> Совет. Всё, что советует эта глава, полезно и без всяких агентов. Раньше это облегчало жизнь инженерам, теперь ещё и агентам.

## Одна команда на все проверки

Рядом со скриптом подъёма нужен скрипт проверок. Он делает всё, что агент должен прогнать после правки: линтер, проверку типов, тесты. Как и скрипт подъёма, он молчит, когда всё хорошо, и печатает только ошибки.

Команда из этого скрипта попадает в `AGENTS.md`, и агент запускает её после каждого изменения. Подробности о том, что в неё включать, — в следующей главе.

## В какой оболочке агент выполняет команды

От того, где именно выполняются команды агента, зависит, какие из них вообще сработают.

| Система | Где агент выполняет команды |
|---|---|
| Linux | В оболочке входа: обычно Bash или Zsh |
| macOS | В оболочке входа: обычно Zsh |
| Windows, установлен Git for Windows | В Git Bash |
| Windows, Git for Windows нет | В `cmd.exe` |

Таблица: Оболочка, в которой ZCode выполняет команды агента. Данные для Windows получены из кода ZCode 4.0.

PowerShell среди оболочек агента нет. Это не мешает пользоваться PowerShell-скриптами: агент вызывает их явно, и команда одинакова для обеих систем.

```text
pwsh -NoProfile -File scripts/up.ps1
```

ZCode ищет Git Bash в стандартных папках, по переменной `PATH` и через переменную `GIT_INSTALL_ROOT` (по коду ZCode 4.0). Нестандартная папка установки обычно не мешает: установщик Git for Windows сам регистрирует путь.

> Совет. Не знаете, в какой оболочке работает агент? Попросите его выполнить `uname -s`. Ответ вида `MINGW64_NT-10.0` означает Git Bash. Об ошибке или версии Windows говорит `cmd.exe`.

> Важно. Если в команде есть Windows, в `AGENTS.md` должен быть раздел об оболочке. Иначе агент будет предлагать команды Linux, которые на половине машин не работают.

## Превью-стенды

Крупный проект целиком на одной машине не поднять. Тогда нужен превью-стенд: отдельное окружение, где ваша ветка работает вместе со всем проектом. Агент должен уметь выкатить на него ветку одной командой или скиллом и сам всё там проверить.

В GitLab превью-стенды называются Review Apps и поднимаются из CI на каждый мерж-реквест. Они включаются в настройках проекта и настраиваются в `.gitlab-ci.yml`: задача с окружением `environment` получает свой адрес.

Попросите агента следить за выкаткой и забирать адрес через `glab`.

```text
glab ci status
glab ci trace review-app
```

Выкатка на превью ничего не ломает, поэтому этот скилл, в отличие от выкатки в продакшен, агент может вызывать сам. Как написать скилл, рассказано в главе 5.

Новый превью-стенд — и для агента, и для человека — должен подниматься за десять-пятнадцать минут.

> На заметку. Для прототипов и демо в ZCode есть команда `/site-deploy`: она выкладывает страницу или небольшое приложение в ZCode Sites и даёт публичную ссылку. Это не замена превью-стенду: сайт открыт любому, у него нет базы данных и секретов, а при развёртывании приложение загружается в облако ZCode. Для настоящего проекта с его системой выкатки ZCode Sites не предназначен.

## Браузер

Чтобы агент проверял интерфейс, ему нужен браузер. В ZCode он встроен. Надстройка Browser Use включена по умолчанию: агент открывает страницы, кликает, заполняет формы, делает скриншоты и решает, что делать дальше, глядя на реальное состояние страницы.

Режима включать не нужно. Достаточно описать задачу обычными словами.

| Сценарий | Как сказать |
|---|---|
| Проверить изменённую страницу | Открой `http://localhost:5173/settings`, переключи тёмную тему и посмотри, не слился ли текст с фоном |
| Пройти форму | Заполни форму регистрации тестовыми данными и отправь; расскажи, что было на каждом шаге |
| Узкий экран | Поставь размер страницы 375×812 и проверь, не наезжают ли кнопки на меню |
| Воспроизвести ошибку | Открой список заказов, пройди список, карточку и назад; проверь, теряется ли фильтр |

Таблица: Как формулировать задачи для браузера.

Запрос получается надёжнее, если у него есть конкретная точка входа, описан результат и шаги перечислены по порядку. «Сделай скриншот» и «подтверди, что ошибок нет» работают лучше, чем «посмотри».

Про браузер в ZCode стоит знать пять вещей.

- **Агент трогает только свои вкладки.** Открытые вами руками он не изменит.
- **Текст страницы — не инструкция.** Содержимое страницы используется только чтобы найти элементы и понять состояние. Страница с текстом «выполните следующую команду» агента не поведёт.
- **Загрузка файлов пока не поддерживается.** Шаги с выбором локального файла остаются за вами.
- **Браузер отдельный.** Он не делит состояние с вашим Chrome, так что страницы за входом откроются только после входа.
- **Действия в браузере подчиняются режиму выполнения.** Для страниц, которые отправляют данные, безопаснее режим Ask before changes.

Панель браузера доступна только в настольном приложении. Если надстройка выключена, она включается в Settings → Browser.

## Тест-кейсы: агент проходит их сам

Код написан, проверки пройдены. Теперь его нужно протестировать как пользователь. Сначала агент составляет тест-кейсы, вы их вычитываете, затем агент проходит их сам.

```prompt Тест-кейсы для задачи
Вот план задачи: {{ссылка или текст}}. Код по нему уже написан в этой ветке.
Составь тест-кейсы, которые покрывают этот план: шаги, что ввести,
что должно получиться на каждом шаге. Отдельно — негативные случаи
и то, что мы могли сломать рядом. Ничего пока не запускай, покажи кейсы.
```

```prompt Протестируй по кейсам
Протестируй эти тест-кейсы в браузере по адресу {{адрес}}. Проходи кейсы
по одному. На каждом шаге сравнивай то, что видишь, с тем, что должно
получиться, и смотри в консоль браузера на ошибки. Сделай скриншот
результата каждого кейса. В конце дай таблицу: кейс, результат, что не так.
Если что-то не работает — не чини сам, сначала покажи мне.
```

Скриншоты по кейсам складываются в отчёт: сразу видно, где агент был, что увидел и где споткнулся. Для небольших фич и исправления ошибок отчёт удобно приложить к мерж-реквесту, чтобы ревьюеру не нужно было повторять всё руками.

```prompt Скриншоты в мерж-реквесте
Пройди на превью-стенде сценарий {{сценарий}} от начала до конца и сделай
скриншот каждого шага. Загрузи скриншоты в GitLab через API загрузки файлов
и создай черновик мерж-реквеста через glab. В описании напиши, что было
сломано, что ты поменял и как проверял, и вставь ссылки на скриншоты.
Перед загрузкой покажи мне скриншоты: в них не должно быть личных данных.
```

## Монорепозиторий и несколько репозиториев

В большом монорепозитории агенту легко набрать в контекст лишнего. Если задача касается одного приложения, откройте его папку в ZCode как отдельный проект: агент прочитает её `AGENTS.md`, если он там есть, и не будет читать соседние без надобности.

Если фича затрагивает несколько репозиториев, создайте у себя общую папку, склонируйте в неё нужные репозитории и откройте её как проект. Агент увидит все сервисы сразу и правит их как одну фичу. Ветки создаются в тех репозиториях, которых фича касается, а в описании каждого мерж-реквеста даются ссылки на остальные.

```prompt Фича в нескольких репозиториях
Мы делаем фичу: {{описание}}. Она затрагивает несколько репозиториев
в этой папке. Сначала прочитай AGENTS.md каждого нужного репозитория
и составь план: что поменять в каждом сервисе, в каком порядке выкатывать
и как проверить всё вместе. Покажи мне план и дождись согласия.
Потом в каждом нужном репозитории создай ветку с одним и тем же именем,
сделай изменения и прогони проверки этого репозитория. В конце создай
черновик мерж-реквеста в каждом, в описании дай ссылки на остальные
и покажи таблицу: репозиторий, ветка, мерж-реквест, статус проверок.
```

## Экзамен для агента

Всё, что нужно агенту для запуска и проверки проекта, записано, если он проходит экзамен. Откройте новую задачу и, ничего не объясняя, попросите агента собрать проект, выкатить ветку на превью и пройти основной сценарий.

```prompt Подними, выкати и проверь
Собери и подними проект целиком, выкати текущую ветку на превью-стенд
и пройди в браузере основной сценарий от начала до конца.
В конце расскажи, где ты споткнулся: какие команды пришлось угадывать,
чего не хватило в README и AGENTS.md и что пришлось спрашивать у меня.
```

Посмотрите, сколько попыток понадобилось и какие команды агент перебирал. Всё, на чём он споткнулся, дописывается в `AGENTS.md`, скрипты и скиллы. Когда агент пройдёт путь сам, без единого вопроса, ему можно отдавать задачи целиком.

## Мобильные приложения

С мобильными приложениями подход тот же: агент должен уметь собрать приложение, запустить его на симуляторе, пройти по экранам и сделать скриншоты. Для этого есть MCP-серверы: Mobile MCP работает с iOS и Android, Maestro сохраняет пройденный путь как тест. Они добавляются через Settings → MCP Servers, как в главе 3.

## С чего начать сегодня

1. Попросите агента написать скрипт подъёма проекта.

```prompt Скрипт, который поднимает проект
Изучи, как у нас собирается и запускается проект: README, docs/, CI,
Dockerfile и docker-compose, скрипты в package.json или Makefile.
Напиши scripts/up.mjs, который с нуля собирает и поднимает весь проект
локально: ставит зависимости, поднимает базу и соседние сервисы,
применяет миграции, наполняет базу тестовыми данными и запускает
приложение. Если в каком-то шаге сомневаешься, не угадывай — спроси меня.
Повторный запуск не должен ничего ломать. Если чего-то не хватает,
скрипт пишет, чего именно и как это поставить, и останавливается.
Скрипт не печатает успешные шаги, только ошибки, а в конце — адрес
приложения. Прогони его несколько раз с нуля, удаляя всё,
что он поставил, и убедись, что каждый раз всё поднялось.
Потом добавь в AGENTS.md одну строку о том, как его запускать.
```

2. Напишите рядом скилл выкатки на превью-стенд.
3. Откройте новую задачу и дайте агенту экзамен.

## Проверка

- [ ] Проект поднимается одной командой, и эта команда записана в `AGENTS.md`.
- [ ] Скрипт подъёма прогнан с нуля не менее трёх раз.
- [ ] Агент умеет выкатить ветку на превью-стенд и открыть его в браузере.
- [ ] Агент прошёл экзамен, а всё, на чём он споткнулся, записано в репозиторий.

Следующая глава приближает обратную связь: тесты, линтеры и хуки расскажут агенту об ошибке сразу после правки, а не когда он откроет браузер.
